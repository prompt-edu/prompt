# PROMPT API Stress & Fuzz Suite

A structured, repeatable harness that drives **every** PROMPT API endpoint to find
what is **slow, degrades under load, errors, or has an access-control gap** - and
actively tries to break the servers via the API only. Built for both humans and
future AIs to read, run, and extend.

## What it does

| Layer | Tool | Purpose |
|-------|------|---------|
| Catalog | `catalog/partial_*.json` | Source of truth: all 249 routes (method, path, roles, params), one file per service. `merge_catalog.py` merges them into `endpoints.json` (generated, gitignored, regenerated by `run.sh` on every run). |
| Auth | `lib/auth.py` | Mint + cache one Keycloak token per role (password grant, public `prompt-client`). |
| Fixtures | `lib/fixtures.py` | Seed 2 isolated courses (A + B for IDOR), phases per type, an enrolled student, per-service data, and Keycloak course-role assignment. |
| Load | `k6/scenario.js`, `k6/exhaustion.js` | smoke / load / spike / soak + all-out exhaustion (flood, multi-MB & deeply-nested bodies). Per-endpoint tagged metrics. |
| Fuzz | `fuzz/fuzz.py` | Input fuzzing, auth matrix (no/forged/alg=none/escalation), cross-course IDOR, file abuse, slowloris. |
| Report | `report/build_report.py` | Merges everything into a prioritized `report.md` / `report.html` / `findings.json`. |

## Running

**Prerequisites:** [`uv`](https://docs.astral.sh/uv/) (Python env + deps) and
[`k6`](https://k6.io/) on your `PATH` (`brew install uv k6`). `uv run` provisions
the Python environment from `pyproject.toml` / `uv.lock` on demand, so there is no
manual `pip install` step.

The suite targets an **isolated** Docker stack (project `prompt-stress`) so it never
collides with another running PROMPT stack. First create the local env file (it is
gitignored), then bring the stack up:

```bash
cp api-stress/stress.env.example api-stress/stress.env   # run.sh also does this automatically

docker compose --env-file api-stress/stress.env \
  -f docker-compose.yml -f api-stress/docker-compose.stress.yml \
  -p prompt-stress up -d \
  db db-team-allocation db-self-team-allocation db-assessment \
  db-interview db-certificate keycloak-db keycloak \
  seaweedfs-master seaweedfs-volume seaweedfs-filer seaweedfs-s3 \
  server-core server-team-allocation server-self-team-allocation server-assessment \
  server-interview server-certificate
```

Then run the suite. The orchestrator lives in `stress/cli.py` and is exposed as
the `api-stress-test` entry point; `run.sh` is a thin shim over it, so these two
forms are equivalent (`uv run --help` lists all flags):

```bash
uv run --project api-stress api-stress-test                    # full run, medium intensity
uv run --project api-stress api-stress-test --smoke-only       # quick reachability + latency baseline
uv run --project api-stress api-stress-test --intensity brutal # all-out
uv run --project api-stress api-stress-test --no-exhaustion    # skip the destructive lane
uv run --project api-stress api-stress-test --fail-on P0       # exit 1 on any P0 finding (what CI does)

# equivalent shim (also creates stress.env, syncs the env, then dispatches):
api-stress/run.sh --smoke-only
```

Output lands in `api-stress/reports/<timestamp>/` (`report.md` first).
`--public-summary DIR` additionally writes a `summary.md` and `findings.json` with
P0 findings reduced to a count, for output that others can read.

### Isolated stack details

Host ports are offset by +10000 to avoid collisions: core `18089`, team-alloc
`18083`, self-team `18084`, assessment `18085`, interview
`18087`, certificate `18088`, Keycloak `18081`, S3 `18334`. Sentry is disabled.
Teardown takes the same file set, because `-v` only removes volumes the loaded files
declare and the override is what renames them:

```bash
docker compose --env-file api-stress/stress.env \
  -f docker-compose.yml -f api-stress/docker-compose.stress.yml \
  -p prompt-stress down -v
```

## In CI

`.github/workflows/test-api-stress.yml` runs on every PR (called from `dev.yml`): it
runs the unit tests (`cd api-stress && uv run pytest`), boots this stack, and runs
`--smoke-only --intensity gentle --fail-on P0 --public-summary <dir>`. So the job
fails on P0 findings, or when the fuzzer crashed and the report lacks its auth and
IDOR results. P1/P2 findings appear in the job summary and the
`api-stress-public-findings` artifact. The `ci-passed` gate (#2414) waits for the job,
so a failure blocks the merge; on PRs that only change docs it is skipped.

The repository is public, so the job never publishes P0 details: the summary only
counts them. When it fails, reproduce the run locally as above and read `report.md`,
and treat a real P0 as a private security advisory. While a known P0 is being fixed
in the advisory, it fails every PR, so an admin may bypass the check to merge
unrelated PRs.
For a longer pass, dispatch the workflow from the Actions tab with a higher
`intensity` and more `scenarios`.

## Extending

- Add/fix a route: edit the relevant `api-stress/catalog/partial_<service>.json`, then
  `uv run --project api-stress api-stress/catalog/merge_catalog.py`.
- Tune intensity: `INTENSITY` presets live in `k6/scenario.js` / `k6/exhaustion.js`.
- Add a fuzz axis: add a method to `fuzz/fuzz.py` and call it in `run()`.

## How findings are prioritized

- **P0** - auth bypass (no/forged/unsigned token accepted), cross-course IDOR, or a service that went DOWN.
- **P1** - 5xx on a valid request, load-induced degradation, oversized-body crash, slowloris.
- **P2** - 5xx on malformed input / non-existent target (missing 404 handling), individually slow endpoints.
